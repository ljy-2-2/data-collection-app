# 小凯实验室数采平台

这是一个使用 PySide6 + Qt Quick/QML 原生界面、运行在采集电脑上的独立 App，提供遥操作采集、UMI rosbag 采集和 Ego 占位页，**不提供、不启动 HIL-SERL**。
遥操作、相机预览、Pico/XR 和编码器数据都留在本机；完成的 Episode 由后台上传器直接登记到数据平台的数据列表。

## 当前功能

- 遥操作：第一步填写任务名称、选择机器人；第二步进入对应机器人的独立操作页。目前支持智元 G2 与 Tianji 天机。G2 保留设备检查、速度/幅度、姿态预览和手动控制。G2 显示三路相机；天机按实际连接数量显示相机，左腕画面在左、右腕画面在右，主相机存在时居中。任务名称随录制数据上传。
- G2 遥操作采集：运行期间使用 Pico 手柄 `A` 开始一段，`B` 完成一段；完成后自动进入平台上传队列。
- UMI：设备检查时自动启动 Galaxis VR 服务和 PICO VR APK，支持双臂/单臂配置、启动服务、开始/完成/放弃一段、监看视频和手动重试上传。
- UMI 放弃回合：确认停止写入并删除该回合目录后，释放当前会话的回合编号，下次采集复用该编号；不再留下空目录。清理失败会提示且保留编号，不报告成功。已保存、已上传和异常保留的回合不会重新编号；隐藏的放弃日志用于防止异常重启后误恢复、误上传。
- UMI 传输诊断：回合结束后生成 `capture-transport.json`，按各相机、夹爪、PICO 等话题记录源时间间隔、DDS 到达间隔、回调排队和写包耗时，统计内存不随时长增长；诊断写入失败不阻止原始包保存。PICO 心跳发送独立于接收循环，避免发送阻塞拖住位姿接收；诊断同时记录心跳发送耗时及失败。原始时间戳、录制阈值及帧内容保持真实，不通过插值掩盖中断。
- UMI 异常保存：设备掉线、软件异常退出或重新上电后，自动恢复已完整写入磁盘的本轮数据，按实际录到的数据结束时间登记并进入上传队列；只有主动“放弃本段”才丢弃。网络或平台暂不可用时保留本地数据，待连接和原采集账号授权恢复后继续上传；独立后台上传服务不会因关闭界面而取消队列。恢复回合标注中断原因和缺失数据，以有效原始 MCAP 上传，不冒充通过完整视频质量检查的正常回合。断电前尚未写入磁盘的内容无法恢复；旧版已删除的回合也无法补回。
- Ego：只保留清晰的空功能位，目前不会连接设备或创建空数据。
- 桌面界面：按原 WebKit 版重建页面布局、配色、相机预览和编码器曲线，Qt Quick 3D 加载完整 CAD 模型；窗口自适应，已移除外部浏览器入口。
- 平台账号：支持“记住账号密码”和“自动登录”；服务器签发登录令牌，后台上传会自动使用当前账号并记录用户名。

- 天机坐标映射参考 `test-teleop` 的相对位姿计算，使用天机厂家模型、硬件接口和完整关节限位；双臂采用一致的镜像关系及连续逆解，在保证末端到达的前提下软性优先选择 J4 负角度和较小关节变化，正角度仍可使用。

- 采集固定本轮实际连接的相机清单，支持仅录制左右腕部；保存所选原始分辨率、硬件亮度读回值、坐标映射版本和实际 SDK 接受的关节指令。MJPEG 不再统一缩小成 640×480。
- 界面文本和错误提示支持选择复制；清理无用组件和已跟踪的 Python 缓存、运行日志及采集样本，保留本机文件而不继续纳入版本管理。
- 遥操页面采用协作者新版布局：桌面宽窗口为模型与较宽的视频面板并排，窄窗口上下排列；相机固定主/左腕/右腕位置，分辨率和亮度通过“相机参数”对话框统一调整。
- 相机连接、错误与机器人检查分开处理；未录制时允许在遥操期间恢复相机预览，画面标题栏提供独立“重连视频”。读取分辨率和亮度直接使用当前流的已验证设置快照，不为读取设置停流或重复打开 USB。实际修改参数仍须先停止遥操与采集。相机异常会阻止或中止相应采集回合，但不会因视频重连失败而把成功的机器人检查改为失败。

- 左右夹爪按实际安装各绕纵轴旋转 180°，安装 yaw 为左 −45°、右 +135°；URDF、工具坐标和显示模型同步，工具点位置和指尖纵轴保持一致。
- 修正复位导致预览锁定：只识别已核对的伺服复位日志；新版客户端与服务协商后，关节采样延迟或反馈错误单独发送健康状态，视频继续显示。单纯的关节采样延迟仅记录质量信息，不再阻止或中断采集；真实反馈错误仍阻止采集，恢复后须收到真实关节反馈。USB、实时任务及未知日志检查继续生效。

**已知相机问题：** 反复切换分辨率或热插拔时，仍复现过连续流中的无效 MJPEG 帧，以及右相机标准 USB 请求超时。正常录制保留严格校验，失败回合不会标为完整或自动上传。相机设置功能和一次完整后端切换流程已通过实测，但上述间歇故障尚未根治；一次恢复出图或断电重启成功不能视为问题已解决。

## Tianji 天机

坐标修正（`vendor_cad_same_facing_v2`）：操作者在机器人背后同向，统一 +X 前、+Y 左、+Z 上。活动模型使用厂家原始臂几何和 `mount_orientation=cad`，URDF 为 `marvin_left_with_gripper.urdf` / `marvin_right_with_gripper.urdf`；废止 `front_back_mirror_v1` 和未经实测的 Y 轴 180° 安装补偿。后者会同时翻转前后和上下，几何镜像还会改变转腕轴关系；两者均不能由“站在背后”推出。硬件编码器角度、零位与左右臂身份保持厂家定义，零位是向两侧水平伸直。FK、IK、雅可比、TCP 和碰撞模型使用同一安装变换，手柄位置与姿态使用同一个右手旋转映射。运行 `python3 scripts/sync_tianji_coordinates.py` 从活动 URDF/安装配置同步 Qt、Web 和 TCP 查看器共用的预览；控制进程在连接机器人前检查预览的安装、关节轴和 TCP，拒绝过期导出。采集元数据与遥测保存坐标版本和会话基准，旧回合不改写。

整臂逆解（`mirrored_reference_local_ik_v8`）：按 `test-teleop/retarget.py` 的 OpenXR → 水平操作者坐标 → 机器人坐标链路计算位置增量和旋转共轭；双臂共享首次接管的水平朝向。普通位形从已接受的关节指令做局部阻尼修正，奇异附近保留有限延续解，旋转换向时丢弃未执行的旧方向目标。求解代价增加关节变化及 J4 正角度的软偏好，偏好项在有限迭代后归零，最后只修正末端位姿；J4 保留完整 −145°～＋60° 硬件范围，不设正负角度硬限制。脱离位置奇异性的有限引导仅针对肘部，并在实际平移超过 2 mm 后激活，原地转腕不再把全臂拉向关节中心。可保持 TCP 位置的旋转方向提高姿态权重并减少数值阻尼；根据相邻实际手柄位姿计算角速度，作为移动目标的末速度，使每个采样点不再被当成必须刹停的终点。静止手柄的末速度归零，关节速度、加速度及实际硬件边界的完整刹停检查始终有效。不可达的位置或奇异方向继续使用稳定的可达分量。左臂通过已验证的完整镜像使用独立求解实例；坐标、TCP、雅可比和耦合腕部限位一起映射。回归覆盖负肘偏好、正角度可达性、小幅转腕的关节总行程、水平及竖直姿态下峰值约 54°/s 的交替旋转和停手。离线测试不能替代实机装配、编码器标定及跟随验证。

故障后回零：选择“零点（默认）”并点击复位，可从 idle/error 状态独立启动，无需 VR/相机预检。按厂家平台的清错→双臂下使能确认→当前反馈保持点→位置模式顺序执行，再逐臂低速将七关节直接回零并下使能，不经过逆运动学。若同臂非相邻连杆的包围盒仍分离、但已进入 15 mm 余量区，优先恢复该臂；预检和运动中均要求间距从当前值恢复，不得继续挤近（反馈容差 0.1 mm），退回余量区外后恢复完整余量。预检的间距状态与实时反馈独立，避免用未来路径的间距误拒绝当前位置。其它连杆对、工具、底座、支架和双臂之间仍保留完整碰撞余量，真正重叠的包围盒不允许豁免。流程可取消，状态会显示当前阶段及间距恢复记录。恢复路径使用厂家硬限位，允许从普通遥操的安全余量边界返回，不再被 URDF 的角度舍入误差误拒绝。真实越过厂家硬限位、持续急停/伺服故障、反馈停止和路径碰撞仍会中止。清错接口的 C 返回类型为 void，以新实时反馈确认结果，不把返回值当作成功标志。

验证边界：厂家 FK/URDF/雅可比交叉检查、六向平移及三轴转动回归只能证明软件链路一致，不能证明真实装配、编码器标定或现场朝向。若与实物仍不符，使用 `PYTHONPATH=teleop_control/vendor/tianji/teleop python3 -m marvin_teleop.installation init --file /tmp/tianji-measurements.json` 建立测量文件；测量所选夹爪 TCP（不是裸法兰），每臂需要至少 3 个分布充分的拟合姿态和 1 个独立检查姿态，再通过实测安装旋转标定，不叠加轴反号。该工具 `init`/`fit` 离线运行，`capture` 只读关节并接收人工测量，不发送运动指令。

在遥操作采集的第一步选择 **Tianji 天机**，下一步进入独立工作台。「上传曲线」可选双臂、左臂或右臂，只决定上传哪些关节和夹爪曲线；遥操作、手动控制和本机采集始终使用双臂与双夹爪，相机按本轮实际连接清单采集。

- 比例、关节速度/加速度位于模式与「其它参数」之间，可直接输入或上下调节；左右夹爪速度和 Kp/Kd 位于小窗。每次进入工作台使用默认值，当次修改自动保存，左右夹爪速度默认均为 10 rad/s。夹爪协议沿用当前力位模式，不自动切换模式。
- 网线连接默认控制器 `192.168.1.190`，连接 Pico 后点击「检查设备」，沿用已安装的 Galaxis VR/RoboticsService。只有新鲜机器人及 VR 数据在线才可开始。
- 「检查设备」会验证 Galaxis VR 是否收到时间戳持续更新的数据。已有连接失效时重建本机 SDK 接收进程，并最多重启一次本机 Galaxis 服务；健康连接保持不变。仅在遥操作、采集和 UMI 均停止时允许检查恢复，不重启 PICO 应用或远端控制器。恢复后仍无新数据会提示检查头显 WORK / Head / Controllers / Send Data，不会把端口监听误报为 VR 数据在线。
- 未接入采集的实时预览会在控制器确认相机故障已清理、可恢复后自动重连；最多连续尝试三次，收到完整路数的新帧后恢复重试额度。全部拔空时持续等待重新枚举；取流健康消息发现相机增减时，按新路数重新建立预览。采集中不自动接续断开的 Episode。
- 「检查设备」仍可在遥操作和采集停止后释放旧预览，再请求一次控制器已校验的故障重连。正常相机热插拔允许重新枚举当前设备；控制器必须确认采集已清理、设备无占用、机器人实时任务和配置未改变。xHCI 错误、USB 复位失败及未知内核日志不按普通热插拔处理。重连不执行 USB 复位、SSH 或服务重启；只有真实新帧到达才显示视频正常，失败采集仍保留失败状态。
- 「相机参数」确认后立即关闭弹窗，在后台一次提交所有修改：正常结束预览并等待冷却后，再连接控制器、读回及写入参数，最后只恢复一次预览。控制器串行处理 TLS 连接，预览未结束前禁止另开状态/设置查询，否则会握手超时。亮度仍使用硬件接口，只改亮度不提交分辨率；多路修改任一路失败会尝试回滚本批次已写入的参数，回滚失败明确报错，未知 USB 故障保留。应用期间不自动重连，取消和未修改确认不操作硬件。此流程修改仅需重启 App 加载，不需要更新控制器服务。
- 遥操作 TCP 为每只夹爪两侧固定转轴所在平面与电机轴线的交点，沿法兰 +Z 方向距安装面中心约 142.226 mm；不随夹指开合变化。左右臂分别使用 URDF 的 `grasp_center_L/R`，控制与显示同步。该位置为 CAD 名义值，更新后须重启 App 加载。
- 模型来自原 `dual_arm_with_grippers.urdf` 和 CAD 网格，包含底座、固定件、双臂和夹爪；支持旋转/缩放。机械臂显示反馈角度，无遥测时显示零点参考；没有夹爪反馈时开度仅示意。
- 相机区域按控制器实际发现的已连接相机生成；`usb-1 / usb-2 / usb-4` 分别标注主相机、右腕部相机、左腕部相机，不改变身份。支持 `stream_camera_selection` 的服务按选中设备连续取流，缺少主相机时直接接收两路腕部视频，不逐帧重开 USB，也不串行等待 2 秒快照冷却。原生 MJPEG 配置为 1024×768、30 fps，实际帧率取决于相机与 USB 链路；Qt 在后台解码并只保留最新显示帧。旧服务保留明确标注的“逐路刷新”兼容模式。同步 Episode 格式仍要求三路完整，双路预览不会冒充三路录制。
- 升级控制器连续视频接口：退出桌面软件，在本机终端运行 `python3 scripts/update_tianji_camera_stream.py`，SSH 密码只在终端输入。脚本核对服务源码哈希、原生文件、相机空闲状态，备份并编译受限 UVC 读取程序，仅更新并重启 `fusion-camera`，审计失败自动回滚。未知相机故障会阻止升级；USB 无首帧/丢包需要检查实际连接。服务保留快照失败详情，取流仍要求真实图像及正常审计收尾。
- 手动控制为每次 10° 步进，复位默认将双臂各 **7 个关节回零**，不重新标定硬件零点、不自动改变夹爪开闭。完整路径预检后，手动移动速度上限为 10°/s，故障后回零为 5.4°/s；手动移动加速度上限为 4°/s²，回零加速度上限为 5°/s²。均受页面中更低的参数上限约束，短行程实际速度取决于平滑加减速。可保存/删除本机姿态。
- 「开始遥操作」后，握把接管对应机械臂、扳机控制夹爪；右手 **A 开始采集、B 结束并保存**（也支持 X/Y）。等待页面显示“采集中”再开始本轮动作；按住按键不会重复创建回合，同时按开始/结束时结束优先。B/Y 不停止遥操作运动；使用「停止控制」或硬件急停停止运动。
- 每侧接管时，以该臂当前 TCP 位姿为起点。首次接管请平视机器人前方：该次头显水平朝向作为双臂共享映射基准，忽略俯仰、侧倾；松握把、转头和短暂断流重新锚定均不改变方向。停止并重新开始遥操或新 VR 会话会重新建立方向基准。修改控制代码后需停止控制并重启 App，让控制进程重新加载。
- 持续接管不再按距本次起点 25 cm 截断位置目标，位置与朝向仍按同一接管基准相对映射；实际运动仍受机械臂可达范围、关节/腕部限位、速度/加速度、碰撞检查和 VR 跳变/失联保护约束。超出可达范围时应松开重新定位，不要继续积累手柄目标偏差。
- 天机遥操作、手动移动和复位均恢复改阻抗前的位置控制流程（`state=1`），发送关节位置目标；不调用 PD 前馈接口，不读取或写入 `JointPIDCtlType`，不配置关节阻抗增益、不保存控制器参数。目标更新频率仍为 100 Hz，原有关节限位、速度/加速度、碰撞和失联保护保持不变，夹爪协议不变。回退 App 代码不会清除控制器已保留的故障或恢复其运行时参数，仍须通过正常停机和预检后才能启动。
- 「其它参数」提供左右夹爪各自的打开/关闭角度，单位为 rad（与文件一致），初值读取 `teleop_control/vendor/tianji/teleop/gripper/config.json` 中对应侧的 `open_rad` / `closed_rad`。停止控制和采集后修改会自动同步该文件及参数指纹，下次遥操作或手动控制生效，界面开度映射同步更新；不改变电流、增益或安全余量。开闭端点必须在启动单圈范围内且行程大于两倍安全余量，允许开闭方向相反；文件不可写或数值不合法会提示保存失败。请按实际机械标定设置，不以软件允许范围代替机械限位。
- 数据在 App 内 `teleop_control/runtime/tianji/episodes/<回合>/` 保存，遥操作采集默认不限时（`max_seconds=0`），按 B/Y 结束并保存；取消采集层 150 ms 反馈新鲜度、300 ms 遥测静默、相机事件等待和相机出帧间隔的自动中止。延迟、缺帧及对齐缺项保留在质量报告中，不补造数据；真实设备故障、连接关闭、写入失败和磁盘不足仍会停止采集。不限时需要先用上述脚本升级控制器相机服务，旧服务仍可预览，但 App 会拒绝开始不限时录制并提示升级。按本轮实际连接的相机录制，支持仅有两只腕部相机；命名为 `head_color`（usb-1）、`right_color`（usb-2）、`left_color`（usb-4）。相机画面下方可分别选择设备原生 30 fps 的 MJPEG 分辨率、调节硬件亮度并恢复默认值。当前腕部相机可选 1024×768、1280×1024、1920×1080；只显示设备声明且当前传输链路支持的档位。应用设置后核验实际画面尺寸，失败恢复之前的采集配置并显示原因；未知硬件故障仍保留。遥操、复位、手动移动及采集期间锁定设置，须先停止再调整。新服务的图像按所选原始分辨率保存为 JPEG，不再缩小为 640×480；MJPEG 直接保存相机编码，旧服务数据继续使用既有转换方式，不创建 native 目录。
- 本机保存实际双臂关节、双夹爪反馈、夹爪对齐来源与误差、实际 SDK 接受的关节指令以及相机索引；`record/actions.jsonl` 与 bundles 中的 action 来自命令，不以关节反馈伪造。元数据同步新版运动学/坐标映射、本轮实际相机清单、各路原生分辨率与硬件亮度读回值。上传时按「上传曲线」筛选临时 tar 内的关节、夹爪、动作和对齐记录，本轮图像及时间戳不变，本机完整原始文件不改写。元数据分别记录实际控制范围 `controlled_sides` 和上传范围 `upload_sides`；已上传回合不自动重传，旧回合沿用原有控制范围与存档格式。
- B/Y 正常结束后，写完索引、时钟对齐、元数据和校验结果，最后才创建 ready 标记。复用 G2 的上传队列：登记导入批次 → 申请上传地址 → 上传单回合 tar → 注册 Tianji Episode → 保存上传回执；同账号登录时失败自动重试、重开 App 后继续、成功后不重复上传。操作栏在“检查设备”左侧显示本次完成的 Episode 数量和采集状态；采集或上传失败时显示原因。
- 单纯的缺帧、延迟或时间对齐缺项允许正常收尾并上传，质量报告不标为合格；真实反馈故障、相机异常、磁盘空间不足等中断会保留不完整回合，但不加入自动上传队列；完整回合的频率/标定质量结论也会保存在元数据中。停止遥操作时仍在录制的回合按中断处理，应先按 B 完成本段。
- Tianji 控制器每路相机的 8 帧发送队列满时，跳过新到的帧并继续取流，保留已排队和正在发送的帧；不覆盖发送中的内存、不补帧、不改原始序号或时间戳。结束记录包含每路累计跳过数量、首末序号及时间范围（范围内不表示每帧均丢失）；这些累计量覆盖整个预览/采集流。采集质量标记会排除明确发生在按 A 之前的损失，跨越边界的损失保守标记为不合格。此行为需更新控制器相机服务；实际断连、损坏帧和发送超时仍按故障处理。
- 相机预览与录制共享同一条连续流，开始录制时订阅当前流并排除开始之前的帧，不重新打开 USB 相机。结束时使用控制器真实收尾、帧计数和时钟对齐结果，再恢复下一条预览流，避免双客户端抢占。控制器报告审计故障（如 `dmesg_sha256`）时会显示原因，不绕过锁定。
- 长时间采集的帧元数据、关节、夹爪、动作与对齐记录使用磁盘暂存和紧凑偏移索引，避免累计百万条 Python 对象后触发秒级垃圾回收、阻塞共用进程中的视频接收。暂存文件为 `record/.working-*.jsonl`，正常完成最终文件和校验后清除；最终保存失败时保留供排查。采集及上传格式不变，控制器的发送超时保护不变。`Frame pipe closed or blocked for 1 second` 表示输出链路阻塞或断开，也可能由电脑端处理停顿引起，不能单凭此消息认定 USB 相机故障；已锁定的服务仍需检查诊断后恢复。
- App 和控制器相机服务更新后，已正常清理的上述管道超时可通过“检查设备”（或“重连视频”）恢复：控制器核验旧取流退出、冷却完成、审计及程序完整性正常、相机接口空闲且无占用，然后清除该故障锁定，App 再建立新的预览。此类故障要求显式点击，后台不自动重试；采集回合仍保持失败，不接续、不更改历史数据。检查被拒绝时保留具体原因，不继续启动预览覆盖错误。该恢复不通过 SSH，不重启服务、不复位 USB，也不发送机械臂运动指令。旧控制器会提示需要一次性更新；对已经人工检查过的旧版管道超时，可在退出 App 后用 `python3 scripts/update_tianji_camera_stream.py --recover-reviewed-pipe-fault` 更新，仅接受精确故障和正常清理记录，并保留既有源码、资源与审计检查。
- 页面失联超过 8 秒请求停止；返回配置时断开天机设备。进程用独占锁和单个厂家连接统一处理遥测、遥操作及手动控制，避免相互抢占。模拟启动 `--mock` 禁止连接天机硬件。

所需 SDK、运动学配置及碰撞模型仅保留在 `teleop_control/vendor/tianji`，运行不依赖桌面的原 SDK 目录；来源和适配点见其中 `UPSTREAM.json`。已同步此次更新的夹爪标定、加速度限制、控制周期和按键定义，也同步既有相机客户端的新色彩转换及恢复接口。仅在没有录制、控制器明确标记故障可恢复并通过清理及审计检查时，有限重试下一条预览流；不重置 USB 主控，不把失败采集恢复成成功。

可选环境变量：`TIANJI_PYTHON` 指向已安装 `numpy`、`pydantic`、`xrobotoolkit_sdk` 的解释器；默认复用 `TELEOP_GDK_PYTHON` 或现有 bot 环境。相机凭据默认保存到当前用户的 `~/.config/xiaokai-lab-data-collection/tianji-camera/client.json`（遵循 `XDG_CONFIG_HOME`），不随版本工作区变化；也可用 `TIANJI_CAMERA_CREDENTIALS` 指定。首次使用可在相机画面右上角设置按钮导入 SDK 的 `client.json`，须保留它引用的证书；软件验证后私密保存配置和证书，再点击「检查设备」连接。旧版工作区的有效配置会自动迁移。导入时须先停止遥操作和采集。换电脑需导入该设备的授权配置并连接实际设备，分发包不包含本机凭据。

相机服务 v2.3.2 若在正常伺服启停后出现 `Audit changed: dmesg_sha256`，先核对控制器日志。确认仅为已知启停消息、停止控制和采集并保持 App 打开后，可在电脑本机的 app 目录运行 `.venv/bin/python scripts/fix_tianji_camera_audit.py --install`。脚本核对空闲状态及服务源码哈希，通过交互式 SSH 备份日志和源码，仅更新相机审计并重启独立的 `fusion-camera`；启动失败回退。修正只允许运动采集期间的精确伺服启停消息，保留原始日志哈希、其它审计检查和静止模式的严格检查。未知服务版本或其它故障会拒绝安装。完成后点击「检查设备」恢复预览；单纯修改电脑端代码不会更新控制器。

首帧超时可先运行 `.venv/bin/python scripts/diagnose_tianji_camera.py` 做只读诊断，报告保存在 `teleop_control/runtime/tianji/camera-controller-diagnostics.json`。确认是主相机 `1-1`、身份为 `0bda:5883`、接口空闲且无进程和内核驱动占用后，可显式添加 `--reset-main-camera` 做一次设备级 USB 复位。该选项要求 App 控制及采集停止，仅针对主相机设备节点调用 USBDEVFS_RESET，并重启独立相机服务；不会重置 USB 主控制器或重试失败的复位。随后验证三路取流，结果仍写入诊断报告。此操作不是断电重启，不保证解决相机硬件故障。[Linux USB 接口说明](https://www.kernel.org/doc/html/v4.10/driver-api/usb.html)

若诊断确认右腕部 `usb-2` 发生 USB 掉线，且服务报告 `Camera interface did not return to idle; Audit changed: dmesg_sha256`，可在人工检查日志后运行 `python3 scripts/restart_tianji_camera.py --restart`。工具只接受已核对的 v2.3.2 故障和服务源码：要求 App 待机、无录制/预览，核对相机身份、占用、接口和连续 5 秒稳定性，备份故障证据后仅重启独立相机服务，再进行三轮各 10 秒的实际图像解码及正常收尾验证。密码由 SSH 在终端读取。不会更改审计规则、复位 USB 或控制机械臂；任一轮失败立即停止，报告保存在 `teleop_control/runtime/tianji/camera-restart-verification.json`。该工具用于恢复已稳定的连接，不能代替对反复掉线的接线、供电或驱动问题的处理。

验证范围：离线模型/控制/API/页面测试，以及三种模式、合成 MJPEG/YUYV → A/B 回合保存 → 模拟平台上传、失败重试和账号切换测试。尚未进行真实机械臂运动或真实平台上传验收。

## 首次安装

分发给其他电脑时使用完整 `.deb`，执行 `sudo apt install ./实际文件名.deb`。
它会安装桌面及 UMI 系统依赖并导入包内镜像。以下脚本步骤仅适用于源码开发环境，
完整安装版不需要另装 Node/npm 或手工构建采集镜像。

在本文件夹打开终端：

```bash
./install-app.sh
```

安装完成后，双击 `数据采集台.desktop`，或从 Ubuntu 应用菜单打开
“小凯实验室数采平台”。它会以独立桌面窗口运行，不显示浏览器地址栏；关闭窗口时
会自动停止该 App 启动的后台采集服务。

安装路径不再要求是某位开发者的桌面目录。请用实际使用 App 的普通用户安装，
不要用 sudo 运行整个安装脚本。安装器会根据当前目录生成用户启动器、应用菜单和
K 图标；首次缺少 .env 时才从模板创建，已有云平台地址和其他配置不会被覆盖。

源码换电脑后需要重新运行 install-app.sh，不要直接复用原电脑的 .venv。
移动安装目录后也应重新安装，以更新 Python 可编辑安装路径和快捷方式。
只刷新当前电脑的快捷方式、不安装依赖或启动采集，可运行：

    python3 scripts/install_desktop.py

GDK/bot 环境及厂商辅助启动器的默认路径按当前用户的主目录查找；非标准位置仍可
通过 TELEOP_GDK_PYTHON、TELEOP_GDK_APP_ROOT 和厂商脚本原有环境变量指定。
完整分发包的构建与安装见 `打包与分发.md`。

直接运行桌面界面（源码环境）：

```bash
./start-app.sh
```

无硬件启动使用 `--mock`。仅启动后台服务使用 `./start-app.sh --backend-only --no-browser`。

独立 App 默认使用 `8011`，以避免与原数据平台的 `8010` 采集服务冲突。如需
更换端口，请同时修改 `.env` 中的 `LOCAL_CONTROL_PORT` 和 `LOCAL_CONTROL_URL`。

## 数据流

UMI 相机换口后需要在“检查硬件”重新确认左右/中央角色。相机绑定同时保存

扩展坞不代表其中的 USB 2.0 设备拥有独立带宽。若日志出现

              │
              ▼
      本机采集服务（127.0.0.1）

              │
              ▼

### UMI 录制就绪

Tianji 与 UMI 的默认单轮采集均不限时，由操作者结束。UMI 已删除 90 秒警告和
120 秒自动停止。UMI 保留开发板的连续性策略：超过 0.2 秒未收到新数据提醒，
连续 1 秒无数据结束并保存；短暂恢复后继续本轮，保存时审计并提取有效连续区间。
TF、追踪有效性和分辨率检查继续有效。旧 JPEG 包转码允许保留带低帧率/长帧间隔
质量警告的视频；时间戳重复/回退及文件损坏仍报错，这不替代原始数据的连续性检查。
停止并重新启动 UMI 采集服务后重新生成配置。天机 PC 修改需重启 App；控制器端
相机停顿策略需由操作者运行 `python3 scripts/update_tianji_camera_stream.py` 更新，
只更新本地源码不会改变已安装服务。本次修改没有连接或更新真实设备。
启动连接、首次通道就绪、停止清理和网络请求的超时用于报告操作失败，不属于单轮
采集时长上限，仍保留；机器人运动控制的失联、急停及电机故障保护保持原有行为。

开始回合时，录制器先等待当前配置启用的相机、PICO 位姿和夹爪消息实际写入
MCAP，才报告录制成功并开始回合计时。仅创建进程、相机预览正常或已有
文件头不会视为就绪；单臂模式不等待关闭侧，低频状态/静态标定话题不阻塞启动。
最多等待 8 秒；超时会说明缺少的通道，进程退出会报告退出码，失败回合不进入
保存和上传流程，未完成文件不会提交平台。不会改写已有回合。

本次更新新增 Python `mcap>=1.2.2,<2` 依赖；从源码更新的电脑需先在
`umi_collection/vendor/galaxis` 中运行 `docker compose build galaxis_core_builder`，
再退出并重新启动 UMI 采集服务。录制开始请求允许等待就绪及失败清理，不应
在等待过程中重复按开始。其他电脑使用新镜像/重新打包的 App。

### UMI 保存与平台导入导出

UMI 头显、双手柄、磁编码器和三路相机均检查源数据连续性；磁编码器短暂投递延迟只提示，不结束正在采集的回合。平台 UMI 检查的真实信号时间戳缺口上限为 100 毫秒，相机也按此上限检查；超过 200 毫秒未收到新数据时提醒，连续 1 秒无数据才结束并自动保存；中间恢复则继续本轮。真实缺口与投递延迟分开审计，保存时把缺口前后的连续区间分别上传（同源回合编号加 `__partNNN`），避免跨缺口训练。正常保存、设备中断和异常退出均进入保留/恢复/上传流程，只有明确点击“放弃本段”才丢弃。异常回合保留中断原因，不伪装成完整成功数据。pi0.5 使用连续动作序列，重采样不会恢复丢失的动作；100 毫秒是当前平台的拒收边界，不代表界内任何延迟都不影响训练。每次保存前复查原始源时间戳和手柄跟踪状态，异常回合提取连续区间，同时完整保留原始文件；过短或仍缺少必要设备数据的片段标记异常，仍须平台筛选。夹爪串口独占打开并核对左右身份；真实串口样本超过 50 毫秒未更新就停止发布旧值。安装版须将完整 `galaxis_core` Python 包挂载到镜像的真实源码路径，避免仅更新桌面源码却继续运行镜像内旧版删除逻辑。

新 UMI 采用 **先可靠暂存、回合结束后生成压缩原始 MCAP、再上传** 的流程。
正式原始数据格式仍为 `umi-mcap-h264-v1`，可离开平台独立使用。
采集期间不运行三路 H.264 实时转码，直接将相机 JPEG 和传感器写入有界 MCAP chunk，
使用 `.mcap.partial` 暂存；它不是已经就绪的正式 rosbag。
停止回合只需收尾刷盘即可开始下一回合，不必等压缩或上传完成。
空闲时后台按帧压缩视频为 H.264，保留所选分辨率、源时间戳和序号，使用标准
`foxglove_msgs/msg/CompressedVideo` 消息；传感器、位姿、关节和标定消息保留原始 CDR 字节，
MCAP chunk 使用 Zstd 无损压缩。视频仍是一次高质量有损压缩，不宣称逐像素无损。
RK3588 使用 MPP / QP 20，电脑使用 libx264 / CRF 18 / veryfast / zerolatency，均不使用 B 帧。
采集和后台压缩均不把整个回合装入内存。压缩器采用有界队列和背压，不再用实时
“编码跟不上”终止正在录制的回合。正式 `.mcap`、`metadata.yaml`、`.compressed-raw.json`
及 `meta.json` 仅在逐帧编码、帧数核对、完整封装和刷盘后发布，之后才允许上传。
`raw-data-status.json` 的 `pending` / `processing` / `ready` 明确区分暂存、整理中、原始数据已就绪；
异常恢复的数据仍带中断和质量审计信息，不能仅凭 ready 就认为适合所有训练。
后台压缩遇到新回合会暂停；上传在开始及每个有界读取块之前检查采集锁，采集结束后继续。
空闲上传连接若超时会刷新地址重试，不删除本地原始数据。正式原始文件发布成功后才清理
该回合自己的正常暂存文件；异常中断的原始证据保留。连续采集会积累未压缩暂存数据，
磁盘容量必须同时容纳暂存和成品，不能只按压缩后的大小估算。
平台连接中断不终止正在录制的本地原始包，
硬件失效及桌面心跳失联仍按保存/恢复规则处理。真实时间戳缺口在写入时检查，
一次正常回合保存为一个主要 `.mcap` 文件。源时间间隔超过 100 毫秒会记录训练质量摘要，
超过 200 毫秒提醒；不足 1 秒的间隔不再自动拆成 `__partNNN`。1 秒无数据仍结束并保存；
恢复工具只对至少 1 秒的真实缺口、时间倒退或无效追踪等异常恢复区间。短缺口保留原始
时间戳和样本，不插值、不补造数据，也不将“可保存”冒充“训练质量合格”。
`meta.json` / `raw-data-status.json` 中的 `source_continuity` 提供各通道计数、最大间隔及有限示例。

PICO 位姿话题使用可靠传输与有限历史缓存；同步刷盘由独立检查线程执行，避免阻塞消息接收。
采集资源保护从启动 ROS 前开始，包含等待设备稳定的阶段。后台处理仍按实际采集状态让出资源；
对无权限调度的子进程不会因此退出整条原始数据整理队列。

完成的 MCAP 包含图像及传感器信息，可以离线读取，不依赖平台或 MinIO 才能恢复内容。
训练 pi0.5 仍需转换为 LeRobot 等训练格式；通用 ROS 话题播放需安装相应消息定义，
包括 `foxglove_msgs` 和录制时的 PICO 自定义消息。平台读取新格式时仅提取/重新封装
已有 H.264 视频，不再次有损编码，也不删除原始 MCAP。旧的 `umi-mp4-v1`
回合及原始 JPEG MCAP 继续兼容，不批量重写历史文件。

默认本机原始目录为 `~/galaxis_data/rosbags/<任务>/<回合>/`；当前开发板对应
`/home/orangepi/galaxis_data/rosbags`。`DATA_MOUNT_PATH`/应用的 UMI 数据根目录
可以指定已挂载外接盘，新回合随该设置保存；`/media`、`/mnt` 下的外接盘未挂载时拒绝启动，
避免静默回落到系统盘。当前 `/media/orangepi/labdisk` 固态盘仅恢复正常挂载，未切换采集路径。

`/var/lib/docker/volumes/data-platform-local_minio_data/_data`。它保存上传后的平台副本，
不等于本机原始目录；原始包、平台副本、平台源视频和导出文件会分别占空间。
将来换机械盘时需单独规划平台存储迁移，不能只改采集目录后就假定系统盘不会继续增长。

## 乐聚 KUAVO 5-W

遥操作配置增加“乐聚 KUAVO 5-W”，桌面和网页均使用独立页面与 `/kuavo` 接口。进入页面、轮询状态不会连接机器人；“检查设备”查询原网络服务与准备记录，并核验 PICO USB、Galaxis VR 应用及持续更新的头显和双手柄输入。已授权且核验为 PICO、应用已启动时会唤醒头显；不启动主控、不发送 CAN 查询。头显检查在独立子进程中进行，原生 SDK 异常不会导致机器人状态检查进程崩溃。

源码已放在 `teleop_control/vendor/kuavo_runtime`，来自备份中的正式 PC 发布快照；不依赖 `Teleoperation-backup-20261019-201949`。独立 worker 防止 KUAVO 与 G2 的同名 Python 包冲突。真实遥操只由操作者点击开始并确认后启动；结束请求使用原版协作退出，不杀机器人主控。原服务仍核验版本、会话所有权和实时反馈。

- 原按键：Grip 控同侧手臂；Trigger 独立控夹爪（0 张开、1 闭合）；松开两侧 Grip/Trigger 后，左 Y 请求回初始姿态、右 B 取消。A/X 不映射天机采集功能。
- 手臂速度及回位姿态继续由机器人端决定。夹爪张开、闭合、速度、加速度支持在“其他参数”编辑保存；当前机器人服务仍需更新其发布配置才会采用新值。
- 网络默认“本电脑网络”，使用安装 App 的这台电脑的网卡和路由，不依赖原电脑的 `kuavons`。旧专用网络保留为可选兼容方式。新电脑在“机器人连接”填写服务 IP、端口、原配置的证书指纹及配套 token；保存只写本地 0600 配置，不连接设备、不自动改网卡。电脑必须能够通过所选网络到达机器人服务地址；PICO 接收服务、SDK 和 USB 连接仍需准备。
- “启动主控”“厂家初始化”“读取夹爪状态”“准备夹爪”仅在用户明确点击时调用原准备接口。启动主控仍要求确认电机编号；夹爪仍要求接受共享 CAN 总线兼容性未完整验证的条件。准备结果不明时先查询，不能当作成功，也不要重复发初始化。
- 本地自动记录每次会话，目录 `teleop_control/runtime/kuavo/episodes/<时间_编号>`：`events.jsonl` 为原客户端输入/机器人诊断回执，`meta.json` 为任务、结束时间和退出报告。它是过程日志，不声称是同步图像数据集，也不会被天机上传器扫描。

当前预留：相机预览/启停/图像录制（原视频依赖 AGX 独立 SSH/ROS 链路）；双腕相机（原工程尚无完整接入）；非手臂部位的实测姿态及达妙夹爪完整外观（现有遥测只有双臂，官方 v63 主体外壳已接入）；关节微调与独立无头显回位（原网络接口未开放，保留会话内 Y/B）；平台格式转换及上传（本次暂略）。这些功能在页面有说明，不使用天机模型或模拟数据替代。

KUAVO 连接配置与 token 在各台机器上单独配置，保存到 App 内 `teleop_control/runtime/kuavo/connection.json`、`token`；不会从其他开发者的目录复制认证凭据或机器人服务端私钥。配置和 token 必须为 0600，Git/安装包排除 runtime；换机通过“机器人连接”保存对应凭据，不能把密钥放进公共安装包。界面不回显已存密钥；重新保存需再次填写，保存成功后清空输入。可用 `KUAVO_PYTHON` 指定已装 PICO SDK 的 Python；默认复用 App 机器人运行环境。

上游接入记录包含 2026-10-23 的 PICO USB、头显唤醒和双手柄输入验证；这些记录不代表本机硬件已经验收。本次源码融合使用离线模拟验证，未启动机器人实机服务或实际遥操。

乐聚页面 01 提供双臂 / 左臂 / 右臂选择、电脑端位移倍率（0.1–1，默认 1 保持原值），以及“其他参数”中的左右达妙夹爪备份参数。单臂通过原 XR 适配器的输入副本屏蔽另一侧 Grip/Trigger；原服务仍负责动作与保护。单臂禁用会同时操作双臂的 Y 回位，右 B 取消保持有效。运行中禁止更改模式及倍率。手臂速度 0.7 rad/s、规划加速度 5 rad/s² 仍为只读。夹爪编辑说明见下方，保存不代表已下发。

02 对齐为机器人、Galaxis VR、Pico 设备三类。PICO 检查 USB 授权、应用进程和数据隧道；Galaxis VR 必须收到有效姿态和持续递增的时间戳，SDK 安装不等于输入在线。空闲时显示最近检查结果，会话中使用实时输入状态，断流及时降级。检查唤醒已运行的头显应用；USB 和应用就绪但无有效输入时，复用天机的本机 XR 接收服务管理器恢复一次，再用新 SDK 实例验证。正常输入不会触发重启，不重装头显应用、不修改手柄映射，不涉及机器人服务。检查受已有跨机器人空闲约束保护。

`teleop_control/assets/kuavo/full_robot.urdf` 与正式版本控制模型 SHA256 一致，`reference.json` 保存备份参数来源及散列；运行不读取桌面备份。页面使用官方 v63 网格绘制可旋转/缩放的实体模型，保持原 URDF 关节位置、转轴和角度单位。仅从原会话 `control_trace` / `ik_trace` 中的 `feedback_rad` 获取双臂实际反馈，不使用 `command_rad`，不增加机器人请求。超过 1 秒没有新反馈或会话退出即标“反馈已过期”；未测量的身体/头部保持参考零位。未启动会话时不能据此查看实时姿态。相机保留左大、右上下三个空白区域。

乐聚姿态外观来自 [LejuRobotics 官方 v63 资源](https://github.com/LejuRobotics/kuavo-ros-opensource/tree/ba5ae219d86076c587e5973c44f5f645ca874a95/src/kuavo_assets/models/biped_s63)，参照用户提供的“产品介绍 / 轮臂产品”图纸。29 个网格精简后存于 `public/kuavo-model.json`（约 3.5 MB），许可证随附 `public/kuavo-model.LICENSE`。`teleop_control/assets/kuavo/visual-manifest.json` 记录固定提交、每个原始文件散列、精简前后面数及尺寸边界变化。只作为显示资产，原控制 URDF 与 vendor 控制代码保持不变，不会从网页下载模型或连接实机。

重建显示资源可运行 `scripts/build_kuavo_model.py <官方文件目录> <GitHub tree JSON>`，构建时使用临时依赖 `fast-simplification==0.1.13`；应用运行不依赖此库。精简后边界变化超过 5 mm 的部件自动保留源网格，防止不规则 CAD 三角面产生尖刺。Qt 与网页共用既有三维显示能力；KUAVO 按关节名直接使用实测弧度值，天机保留角度转换与夹爪映射。没有实时反馈时显示参考姿态；身体、头部以及夹爪开合不宣称实时。


### 乐聚换机与夹爪参数（2026-10-23）

“任何安装本 App 的电脑”是使用本机网络和随 App 提供的代码，不表示任意操作系统或缺少驱动的电脑都即装即用。需要 App 支持的系统/架构、可达机器人的网络、该机器人的连接凭据，以及与 Python 环境匹配的 PICO SDK 和接收服务。完整机器人运行环境可复用 App 的 XR 依赖；源码运行可通过 `KUAVO_PYTHON` 指定环境。当前没有修改用户网卡或实机服务，也没有重新生成安装包。

左右夹爪各支持张开位置（rad）、闭合位置（rad）、速度（0.01–15 rad/s）、加速度（大于 0、至多 200 rad/s²）。原标定、总线编号、读回记录、电流、力矩和保护限制保持原样；改动端点标记为操作者设置，不伪造新的测量。点击确认后使用原乐聚校验器离线验证，原子保存到 `teleop_control/runtime/kuavo/gripper_config.json`；取消丢弃未提交草稿，“恢复原项目值”也仅改草稿，需确认才保存。重开窗口和重启 App 后读取保存值。

机器人实际读取不可变服务发布包 `core.json` 中的夹爪配置，原协议没有写参数请求。因此当前保存的 JSON 是待发布配置，**不能直接替换机器人发布包里的某个文件**（完整性校验会拒绝）。仍需按机器人服务发布流程将该 JSON 作为 `gripper_config` 生成新发布包、由现场操作者更新服务；本轮没有完成机器人端在线改参接口或服务发布。App 不会绕过该校验或自动重启实机。检查设备会比较机器人服务的配置 SHA256 与本机 JSON：一致显示最近核验一致，不一致显示待应用并禁用开始；启动 worker 再次核验，避免检查后服务发生变化。保存参数并非重新标定或硬件验收。

日常操作顺序：

1. 进入“遥操作采集”，选择“乐聚 KUAVO 5-W”及任务。首次换机先保存“机器人连接”，保持“本电脑网络”。
2. 连接 PICO USB，在头显中开启 Send Data，并准备 PICO 接收服务；点击“检查设备”。检查会唤醒已授权的 PICO，并在启动遥操前独立验证输入；只读取机器人服务信息，不会自动启动主控或初始化电机。若仍没有数据，请在头显中确认 WORK、Head、Controllers 和 Send Data；这些应用内开关没有可用的 ADB 设置接口。
3. 选择双臂或单臂，设置位移倍率；检查夹爪参数是否与服务一致。现场按厂家流程准备主控和夹爪：只有确认尚未准备时才点击对应准备按钮，已有主控不要重复启动，已有初始化不要重复执行。
4. 确认共享总线使用条件、先松开两侧 Grip / Trigger，然后点击“开始遥操作”并确认。握住同侧 Grip 控制手臂；Trigger 接管夹爪。双臂模式中松开两侧 Grip / Trigger 后可按左 Y 回位，右 B 取消；单臂模式禁用 Y。
5. 点击“结束遥操作”，等待会话退出。过程日志自动留在 App 内；相机、同步图像采集和平台上传仍未接入，A/X 不承担天机的录制功能。
